## The OS images

`bios.kr32` and `kernel.kr32` are build products, not fixtures, and nothing under `src/resources/os` is committed. The configure resolves `krc` through `cmake/KrGuest.cmake`, and a custom command runs `kr32os/build.ps1` (Windows) or `kr32os/build.sh` (Linux) into `build/<preset>/os-images`; `tools/embed_os` then turns the pair into `generated/os/embedded_os.cpp`. The images are per host because the compiler embeds source paths in the debug sections.

`kr32_os_images_match_source` (on by default, `KR32_CHECK_OS_IMAGES`) rebuilds them twice and requires both builds, and the copy the VM embedded, to match byte for byte, so a nondeterministic OS build fails there rather than varying the embedded kernel.

Each regeneration starts from an empty directory: the script caches `user_*.kro` in its output, and a rerun after a compiler change would otherwise pack stale objects.

## Commit and test cadence

During an optimization inner loop, do not commit every change.

- **Accumulate first.** Delay the commit until the tree holds **five functional
  changes**, or the diff reaches **180 changed lines of code**. Count `src/` and
  `tests/` (added plus removed); exclude `docs/` and `implementation.md`. Either
  limit ends the batch.
- **Inner loop.** After each change, build and run only the focused tests for the
  code touched (`kr32_tests.exe --source-file="*test_<area>.cpp"`, or the single
  ctest entry). Do not run the full suite per change.
- **Before the commit.** Run the full regression: the Windows and WSL gates
  above. Anything red blocks the commit.
- **One commit per batch**, with the running-log entry and the measurements for
  the whole batch. If a change is risky or the tree must be left green for
  someone else, commit early and say why.

## Architecture boundaries

- `src/platform` is the only OS/SDL boundary. `src/ui` must not include OS or SDL headers; `tests/boundary` enforces this.
- The installed krc toolchain compiles guest C/C++, and the `kr32` executable loads, runs, disassembles and debugs the resulting `.kr32` images. There is no in-tree compiler, assembler, linker or runtime to keep in step.

## Known traps

- CMake, Ninja, and `ctest` are not on `PATH` in a plain PowerShell; use the Visual Studio developer environment or the full paths in `AGENTS.md`. A failing `where cmake` is not a missing toolchain.
- The krc package's CRT configuration must match the KR32 build: a Debug `krc-toolchain.lib` links into a Release build and fails with unresolved `__imp__CrtDbgReport`. Use the Release-CRT krc install for a Release configure.

## WSL builds

A WSL build runs on an ext4 mirror, never on `/mnt/c`. A build under the mount carries
mount paths in its debug data and its file timestamps are too coarse for incremental
work, so the mirror is refreshed with the family tool and the gate runs from there:

    sh ../krcompiler/scripts/kr-mirror.sh kr32
    cd ~/mirrors/kr32 && bash scripts/run-gate.sh

A gate that supports it does this itself when it is started from a `/mnt/c` path: it
prints the mirror it used and re-executes there, and `--in-place` opts out for the
rare case where a mount build is intended. Editing happens on Windows; the mirror is
disposable and is never committed.
