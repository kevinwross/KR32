# KR63 Instruction Set and Machine Specification

> **Status.** Design target for the KR63 virtual CPU, not a description of
> shipped code. Revision 2 changes three things from the original proposal: the
> implementation language is **C++20** (the Python prototype is discarded), the
> instruction encoding is **frozen as v1**, and the CPU gains a **page table
> register** plus a two-level memory-management unit.

## 1. CPU State Model

Each core owns:

| State | Width | Notes |
| --- | --- | --- |
| `R0..R15` | 32 | independent registers; there is no hard-wired zero register |
| `PC` | 32 | address of the next instruction; always 4-byte aligned |
| `SP` | 32 | stack pointer; the stack grows down |
| `FLAGS` | 32 | status bits below |
| `MODE` | 1 | user or kernel |
| `IE` | 1 | interrupt enable |
| `PENDING_IRQ` | 16 | pending hardware interrupt lines |
| `CR0..CR11` | 32 each | control registers, §5 |
| `cycles` | 64 | retired instruction count |
| `reservation` | 33 | pending `LL` address plus a valid bit, §12.2 |
| `enabled` | 1 | core participates in the machine |
| `halted` | 1 | core has executed `HALT` or stopped on a fatal fault |

`MODE` and `IE` are views of `FLAGS.K` and `FLAGS.I`; there is one canonical copy
of each bit.

### Flags register

| Bit | Name | Meaning |
| --- | --- | --- |
| 0 | Z | result was zero |
| 1 | N | result bit 31 set |
| 2 | C | carry out / no borrow |
| 3 | V | signed overflow |
| 4 | I | interrupts enabled |
| 5 | K | kernel mode active |
| 6..31 | | reserved; read as zero, ignored on write |

### Machine configuration

`MAX_CORES = 128`, of which only core 0 is enabled at reset; §12 covers how the
others are brought up. Execution uses the deterministic cooperative scheduler of
§12.3, so v1 has a scheduler but no host-thread parallelism. Per-core `cycles`
counts retired instructions; delivering a vector costs one additional cycle.
The machine also keeps a global `ticks` counter, the sum of retired
instructions, which is the only clock in the system (§13.5).

## 2. Memory and Addressing Model

### 2.1 Physical address space

| Range | Region |
| --- | --- |
| `0x00000000..0x0000FFFF` | guard page: never backed, every access faults |
| `0x00000000..0xFFF0FFFF` | RAM from physical 0; 4 MiB firmware reservation, 128 MiB installed by default |
| `0xFFF10000..0xFFFEFFFF` | fourteen memory-mapped I/O pages: inter-processor block (§12.4), IRQ route table (§13.6), then device windows |
| `0xFFFF0000..0xFFFFFFFF` | ROM: reset vector and BIOS |

RAM starts at physical 0 and grows upward, so installed RAM
occupies `RAM_BASE .. RAM_BASE + ram_size - 1`. The maximum supported size is
`0xFFF00000` bytes, bounded by the I/O window.

`ram_size` is chosen at construction. ROM is one 64 KiB read-only page at the
top of the address space. The guard page belongs to neither RAM nor ROM, which
makes address zero an invalid physical address: a NULL dereference faults with
paging off and with paging on, instead of silently reading or writing storage.
The 64 KiB size matches Linux's `mmap_min_addr` convention and catches null
pointers plus small offsets.

### 2.2 Page size

Pages are **64 KiB (2^16)**. The low 16 bits of a virtual address are the page
offset and pass through translation unchanged; only the high 16 bits are
translated. This matches the address map above: the guard is page 0, RAM begins
at page 1, the I/O window is pages `0xFFF1..0xFFFE`, and ROM is page `0xFFFF`.

The MMU is parameterised by `PAGE_SHIFT = 12`, `PAGE_SIZE = 1 << PAGE_SHIFT`,
`PAGE_MASK = PAGE_SIZE - 1`, `VPN_BITS = 32 - PAGE_SHIFT`,
`DIR_BITS = LEAF_BITS = VPN_BITS / 2`. A future switch to 4 KiB pages is a
constant change plus a revision of §2.1, not a redesign. All statements below
are for the 64 KiB default.

### 2.3 Virtual-to-physical translation

When `MCTL.PGE` is clear, translation is the identity and virtual addresses are
physical addresses. When it is set:

```text
vpn  = VA >> 16                 // 16 bits
dir  = dir_table[vpn >> 8]      // 8 bits: VA[31:24]
pte  = leaf_table[vpn & 0xFF]   // 8 bits: VA[23:16]
PA   = (pte & 0xFFFF0000) | (VA & 0xFFFF)
```

`dir_table` is the 256-entry table whose physical base is held in `PTBR`.
`leaf_table` is the 256-entry table whose physical base is the directory entry's
page number. A full 256 x 256 walk covers the entire 32-bit virtual space. With
8 MiB of RAM the map needs two leaf tables: directory entry 0 covers RAM pages
1..128, and directory entry 255 covers the I/O window and ROM.

### 2.4 Page-table entry format

Both levels use the same 32-bit entry layout:

```text
bits 31..16  PPN      physical page number (PA >> 16)
bits 15..12  reserved, must be read as zero and written as zero
bits 11..0   flags
```

| Bit | Flag | Meaning |
| --- | --- | --- |
| 0 | V | entry present |
| 1 | W | writable |
| 2 | U | accessible from user mode |
| 3 | X | instruction fetch allowed |
| 4 | A | accessed (set by hardware) |
| 5 | D | dirty (set by hardware on write) |
| 6 | G | global; survives a translation invalidate |
| 7..11 | | reserved |

A directory entry uses bit 0 as `V` and bits 31..16 as the physical base of a
leaf table; other flag bits are reserved there. Every table is page-aligned, so
a leaf table occupies one 64 KiB page even though only 1 KiB is used. That waste
is a deliberate simplification for v1.

Physical address reconstruction is `PA = (entry & 0xFFFF0000) | page_offset`.
Because physical page 0 is the guard page, it is never a valid PPN, and the leaf
entry that would map it is never present.

For a hypothetical 4 KiB page size the present bit would stay at bit 0, the PPN
field would widen to bits 31..12, and the reserved nibble would disappear.

### 2.5 Access permission checks

Translation resolves each byte of an access through its own page, so an access
that crosses a page boundary is legal when every page involved is mapped and
permitted. The fault address for a crossing access is the first failing address.

| Access kind | Requirements |
| --- | --- |
| instruction fetch | `V`, `X`, and `U` when in user mode |
| load | `V`, and `U` when in user mode |
| store | `V`, `W`, and `U` when in user mode |

`MCTL.WP`, when set, additionally requires `W` for kernel-mode stores; when
clear, the kernel may write read-only pages (useful for copy-on-write). The
hardware sets `A` on any successful translation and `D` on a successful write.
User mode must have `U` at both levels.

### 2.6 Faults

- **`#PF` (vector 4)** — a translation or permission failure while paging is
  enabled. `FAR` receives the faulting virtual address. The error code is
  `bit0 P | bit1 W | bit2 U | bit3 X`, where `P` is 0 for not-present and 1 for
  a permission violation.
- **`#GP` (vector 5)** — an access that cannot be described by a page fault:
  a store to ROM or an access outside installed storage while paging is
  disabled, an invalid control-register write, an out-of-range software vector,
  or a privileged instruction executed in user mode. `FAR` is not updated.
- **`#ALIGN` (vector 6)** — an instruction fetch from an address that is not a
  multiple of four.

The guard page is outside installed storage, so a NULL access produces `#GP`
while paging is off. Once paging is on the page is simply not present, so the
same access produces `#PF` with `P = 0`.

### 2.7 Physical access

Only the MMU and reset logic may read or write physical memory. The memory
controller exposes `read_physical` / `write_physical` internally; guest code has
no physical-address access and no instruction that bypasses translation. Page
tables therefore live in guest RAM and are edited through a kernel identity map,
which the BIOS installs before enabling paging.

The kernel identity map covers ROM, installed RAM, and the I/O window. The guard
page is never mapped, in any mode.

Device models use the same physical interface. DMA bypasses translation and
permission checks entirely, and is restricted to backed RAM (§13.2).

### 2.8 Alignment

Instruction fetch and branch targets must be four-byte aligned (`#ALIGN`
otherwise). Data accesses of any width are allowed at any byte address, subject
only to the page checks above.

## 3. Instruction Format (frozen v1)

Instructions are 32-bit fixed-length, optionally followed by one 32-bit
extension word.

### 3.1 Base word

| Bits | Field |
| --- | --- |
| 31..26 | opcode (6) |
| 25..22 | destination register (4) |
| 21..18 | source A register (4) |
| 17..14 | source B register or addressing mode (4) |
| 13 | `E`: an extension word follows |
| 12 | `L`: the payload is a literal |
| 11..0 | inline value, signed 12-bit |

### 3.2 Rules

1. `E = 1` means the next four bytes are a little-endian 32-bit payload and the
   instruction is eight bytes long. The inline field is ignored.
2. `E = 0` means the payload is the inline field sign-extended from 12 bits, and
   the instruction is four bytes long.
3. `L = 1` means the payload is a literal, immediate, or displacement. `L = 0`
   means the 17..14 field names a register. Whether `L` is consulted is
   opcode-dependent; see §4.
4. At most one extension word. Chained extensions are not part of v1.
5. Reserved opcodes and reserved addressing modes are rejected with `#UD`; they
   are never treated as no-ops.
6. The assembler always emits `E = 1` for literals, labels, and displacements so
   that instruction sizes are predictable regardless of operand magnitude.

### 3.3 Addressing modes

For `LOAD`, `STORE`, `LOAD8`, `LOAD16`, `STORE8` and `STORE16` the 17..14 field
selects an addressing mode:

| Value | Mode | Effective address |
| --- | --- | --- |
| 0 | register direct | not a memory mode; the field names a register |
| 1 | immediate literal | the payload is data, not an address |
| 2 | register indirect | `[RsrcA]` |
| 3 | indexed | `[RsrcA + disp]` |
| 4 | stack-relative | `[SP + disp]` |
| 5 | absolute | `[disp]` |
| 6 | PC-relative | `[instruction address + disp]` |
| 7..15 | reserved | `#UD` |

The PC-relative base is the address of the instruction itself, not of the
following instruction.

`LEA` uses these modes to compute an address without accessing memory, so it
never faults on an unbacked target. Base+index is therefore two instructions
rather than a mode: `LEA Rd, [Rb + disp]` followed by `ADD Rd, Rd, Ri`.

This field is an addressing mode only for the memory instruction family.
Branches do not use it: a literal target is selected with `L = 1` and carries an
absolute address, and a register target uses `L = 0` with the register in the
17..14 field.

## 4. Instruction Set

### 4.1 Opcode map

| Op | Mnemonic | Op | Mnemonic | Op | Mnemonic |
| --- | --- | --- | --- | --- | --- |
| 0x00 | MOV | 0x0B | NOT | 0x16 | JNS |
| 0x01 | LOAD | 0x0C | SHL | 0x17 | CALL |
| 0x02 | STORE | 0x0D | SHR | 0x18 | RET |
| 0x03 | ADD | 0x0E | ROL | 0x19 | PUSH |
| 0x04 | SUB | 0x0F | ROR | 0x1A | POP |
| 0x05 | MUL | 0x10 | JMP | 0x1B | INT |
| 0x06 | DIV | 0x11 | JZ | 0x1C | IRET |
| 0x07 | CMP | 0x12 | JNZ | 0x1D | SYSCALL |
| 0x08 | AND | 0x13 | JC | 0x1E | HALT |
| 0x09 | OR | 0x14 | JNC | 0x1F | BRK |
| 0x0A | XOR | 0x15 | JS | 0x20 | reserved |

| Op | Mnemonic | Op | Mnemonic |
| --- | --- | --- | --- |
| 0x21 | LOAD8 | 0x25 | STORE8 |
| 0x22 | LOAD16 | 0x26 | STORE16 |
| 0x23 | reserved | 0x27 | MOD |
| 0x24 | reserved | 0x28 | RDCR |
| 0x29 | WRCR | 0x2A | NOP |
| 0x2B | LL | 0x2C | SC |
| 0x2D | FENCE | 0x2E | LEA |
| 0x2F..0x3F | reserved | | |

`LOAD`/`STORE` are the 32-bit forms. Anything not listed is reserved and raises
`#UD`.

### 4.2 Data movement

| Instruction | Effect | Flags |
| --- | --- | --- |
| `MOV Rd, Rs` / `MOV Rd, #imm` | `Rd = source` | unchanged |
| `LOAD Rd, [addr]` | `Rd = u32 at addr` | unchanged |
| `LOAD8 Rd, [addr]` | `Rd = zero-extended u8` | unchanged |
| `LOAD16 Rd, [addr]` | `Rd = zero-extended u16` | unchanged |
| `STORE Rs, [addr]` | `u32 at addr = Rs` | unchanged |
| `STORE8 Rs, [addr]` | `u8 at addr = Rs[7:0]` | unchanged |
| `STORE16 Rs, [addr]` | `u16 at addr = Rs[15:0]` | unchanged |
| `LEA Rd, [addr]` | `Rd = effective address` as a value | unchanged |

Sized signed loads (`LOAD8S`, `LOAD16S`) are not part of v1; they can take
reserved opcodes later.

### 4.3 Arithmetic and logic

| Instruction | Effect | Flags set |
| --- | --- | --- |
| `ADD Rd, Rs, x` | `Rd = Rs + x` | Z N C V |
| `SUB Rd, Rs, x` | `Rd = Rs - x`, `C` = no borrow | Z N C V |
| `CMP Rs, x` | flags of `Rs - x`, no write | Z N C V |
| `MUL Rd, Rs, x` | `Rd = low32(Rs * x)` | Z N, `V` = high32 nonzero, `C` = 0 |
| `DIV Rd, Rs, x` | `Rd = Rs / x` unsigned; `#DIV0` if `x = 0` | Z N, `C` = `V` = 0 |
| `MOD Rd, Rs, x` | `Rd = Rs % x` unsigned; `#DIV0` if `x = 0` | Z N, `C` = `V` = 0 |
| `AND`/`OR`/`XOR Rd, Rs, x` | bitwise | Z N, `C` = `V` = 0 |
| `NOT Rd, Rs` | `Rd = ~Rs` | Z N, `C` = `V` = 0 |

The low 32 bits of `MUL` are identical for signed and unsigned operands; `V`
reports unsigned overflow. `DIV`/`MOD` are unsigned in v1, matching the
borrow-carry convention of `SUB`/`CMP`. Signed variants can be added later
without changing the format.

### 4.4 Shifts and rotates

The count is the low five bits of the second operand, so the range is 0..31.

| Instruction | Effect | Flags set |
| --- | --- | --- |
| `SHL Rd, Rs, n` | `Rd = Rs << n` (logical) | Z N, `C` = last bit shifted out, `V` = 0 |
| `SHR Rd, Rs, n` | `Rd = Rs >> n` (logical) | Z N, `C` = last bit shifted out, `V` = 0 |
| `ROL Rd, Rs, n` | rotate left | Z N, `C` = last bit rotated out, `V` = 0 |
| `ROR Rd, Rs, n` | rotate right | Z N, `C` = last bit rotated out, `V` = 0 |

A count of zero leaves the destination unchanged and leaves `C` unchanged.

### 4.5 Branches and stack

| Instruction | Effect |
| --- | --- |
| `JMP target` | `PC = target` |
| `JZ`/`JNZ` | jump when `Z` set / clear |
| `JC`/`JNC` | jump when `C` set / clear |
| `JS`/`JNS` | jump when `N` set / clear |
| `CALL target` | push the address after the complete instruction, then jump |
| `RET` | pop the return address into `PC` |
| `PUSH Rs` | `SP -= 4`, store `Rs` |
| `POP Rd` | load `Rd`, `SP += 4` |

Conditional branches do not modify flags. `CALL` pushes the address after the
whole instruction, including any extension word.

### 4.6 System

| Instruction | Effect |
| --- | --- |
| `INT vector` | software interrupt; vector must be 32..255 |
| `SYSCALL vector` | software call; vector must be 32..255 |
| `IRET` | return from an interrupt or exception frame |
| `HALT` | stop the core; kernel mode only |
| `BRK` | raise `#BRK` (vector 3) |
| `NOP` | no effect; advances `PC` |
| `FENCE` | full memory barrier; a no-op under the model in §12.1 |
| `LL Rd, [addr]` | load a word and establish a reservation (§12.2) |
| `SC Rs, [addr]` | store if the reservation holds, reporting success in `Z` |
| `RDCR Rd, CRn` | `Rd = CRn`; kernel mode only |
| `WRCR CRn, Rd` | `CRn = Rd`; kernel mode only |

`INT`/`SYSCALL` with a vector below 32 raise `#GP`, so software vectors can
never collide with exceptions or hardware interrupt lines.

### 4.7 Example encodings

```text
MOV R1, R2          opcode MOV, dest R1, srcA R2, L=0
MOV R1, #42         opcode MOV, dest R1, L=1, payload 42
ADD R3, R1, R2      opcode ADD, dest R3, srcA R1, srcB R2, L=0
LOAD R4, [R5 + 8]   opcode LOAD, dest R4, srcA R5, mode 3, payload 8
LOAD8 R4, [R5 + 8]  opcode LOAD8, dest R4, srcA R5, mode 3, payload 8
JMP 0x00400000      opcode JMP, L=1, extension word 0x00400000
JMP label           opcode JMP, L=1, extension word (resolved absolute address)
JMP R7              opcode JMP, L=0, srcB R7
```

## 5. Control Registers

| CR | Name | Purpose |
| --- | --- | --- |
| 0 | `IE` | global interrupt enable; reads as `FLAGS.I` |
| 1 | `IMR` | hardware interrupt mask, bits 0..15 |
| 2 | `IRQ` | pending / active interrupt bitmap, bits 0..15 |
| 3 | `VTBR` | interrupt vector table base (virtual address) |
| 4 | `PRIV` | current privilege; reads as `FLAGS.K` |
| 5 | `ESR` | exception status: vector number of the most recent delivery |
| 6 | `KSP` | kernel stack pointer |
| 7 | `MISC` | reserved for future system status |
| 8 | `PTBR` | page table base register |
| 9 | `FAR` | fault address register |
| 10 | `MCTL` | memory control |
| 11 | `COREID` | read-only core index, 0..127 |
| 12..15 | | reserved; access raises `#GP` |

### 5.1 `PTBR` — page table base register

`PTBR` holds the **physical** base address of the top-level page directory.
It is physical because the page walk must never re-enter translation: a fault
handler that had to fault in its own page tables could not recover. The value
must be page-aligned; the low 16 bits must be zero. A misaligned write raises
`#GP` rather than being silently masked.

`PTBR` is per-core, so each core can run in its own address space. Writing it
requires kernel mode and invalidates translation state.

### 5.2 `FAR` — fault address register

`FAR` receives the virtual address that caused the most recent `#PF` or
`#ALIGN`. It is not updated by `#GP`. The kernel may read and write `FAR`, which
lets a handler save and restore it across nested faults.

### 5.3 `MCTL` — memory control

| Bit | Name | Meaning |
| --- | --- | --- |
| 0 | `PGE` | paging enable; clear at reset |
| 1 | `WP` | kernel stores to read-only pages fault when set |
| 2..31 | | reserved |

Writing `MCTL` requires kernel mode and invalidates translation state. Paging is
always disabled at reset, so early boot code addresses physical memory directly.

### 5.4 `COREID` — core identifier

`COREID` is read-only and holds the index of the reading core, 0..127. It lets
one image run unchanged on every core, which is how a secondary core locates its
slot in the inter-processor block and its own boot record. Writing it raises
`#GP` in every mode.

### 5.5 Privilege rules

| Operation | User mode | Kernel mode |
| --- | --- | --- |
| read `CRn` | `#GP` | allowed |
| write `CRn` | `#GP` | allowed |
| write `COREID` | `#GP` | `#GP`, it is read-only |
| `HALT` | `#GP` | halts the core |
| `IRET` | `#GP` | allowed |
| `BRK` | allowed | allowed |
| `INT`/`SYSCALL` | allowed | allowed |

## 6. Exceptions, Interrupts and Privilege

### 6.1 Vector map

The vector table is 256 little-endian 32-bit entries at virtual address `VTBR`;
entry `v` holds the handler address for vector `v` and must be four-byte
aligned.

| Vector | Source |
| --- | --- |
| 0 | reserved |
| 1 | `#UD` invalid opcode or encoding |
| 2 | `#DIV0` divide by zero |
| 3 | `#BRK` breakpoint |
| 4 | `#PF` page fault |
| 5 | `#GP` general protection |
| 6 | `#ALIGN` misaligned instruction fetch |
| 7 | `#DF` double fault |
| 8..15 | reserved |
| 16..31 | hardware interrupt lines 0..15 |
| 32..255 | software `INT` / `SYSCALL` vectors |

### 6.2 Delivery

An exception or interrupt transfers control as follows:

```text
deliver(vector, error_code):
    victim_pc = PC at the faulting instruction, or the next instruction for an
                asynchronous interrupt
    saved_sp  = SP
    if user mode:
        SP = KSP
    push(error_code)
    push(saved_sp)
    push(FLAGS)
    push(victim_pc)
    FLAGS.K = 1
    FLAGS.I = 0
    PC = *(VTBR + vector * 4)
```

Because the stack grows down and entries are pushed in that order, `SP` points
at the saved `PC` on entry to the handler. Interrupt and exception frames share
one shape; asynchronous interrupts push an error code of zero.

For a fault, the saved `PC` names the faulting instruction, so `IRET` retries
it. For an asynchronous interrupt, the saved `PC` names the next instruction.

Traps and software interrupts — `BRK`, `INT`, `SYSCALL` — are not faults: they
save the following instruction, so `IRET` resumes after them instead of
retrying. A handler that steps over `BRK` therefore needs no special case.

### 6.3 Error codes

| Vector | Error code |
| --- | --- |
| `#PF` | `bit0 P \| bit1 W \| bit2 U \| bit3 X` |
| all others | zero |

`ESR` receives the delivered vector number regardless of the frame's error code.

### 6.4 `IRET`

`IRET` requires kernel mode and an interrupt frame. It pops the four words in
reverse order, restores `FLAGS` (and therefore `MODE`), restores `SP`, and
resumes at the saved `PC`. The frame is not architecturally distinguishable from
ordinary stack data, so a handler must not disturb it.

### 6.5 Double fault

If an exception occurs while the CPU is already delivering one — for example a
fault while pushing the frame or fetching the vector — the CPU delivers `#DF`
(vector 7) instead. If `#DF` delivery itself fails, or a fault occurs while
executing the `#DF` handler, the core stops and the machine records a
diagnosable halt reason. A normal fault inside an ordinary handler does not
escalate; it is delivered to that handler like any other fault.

At reset `VTBR` is zero, so a fault taken before the BIOS installs a vector
table cannot be delivered: the vector fetch itself faults, escalates to `#DF`,
and halts. That is the intended failure mode for a corrupt boot image.

### 6.6 Hardware interrupts

`Machine::request_interrupt(line)` sets bit `line` of `IRQ` for lines 0..15.
Before each instruction the CPU selects the lowest pending line that is
unmasked in `IMR` and enabled by `IE`, delivers vector `16 + line`, and clears
the pending bit. Software vectors bypass `IE`, `IMR`, and `IRQ` entirely.

One core raises a line on another through the inter-processor block (§12.5).
The target's `IMR` and `IE` then decide delivery, exactly as for an external
device; there is no broadcast. Device-raised lines are steered by the IRQ route
table (§13.6) before delivery.

## 7. Boot and BIOS

### 7.1 Reset sequence

1. Power on.
2. The CPU enters kernel mode with interrupts disabled and paging off.
3. `PC` is loaded from the little-endian word at the ROM base, `0xFFFF0000`.
4. `SP` and `KSP` are set to `(RAM_BASE + ram_size) & ~15`.
5. The BIOS runs from the ROM page at `0xFFFF0000`.
6. The BIOS installs the interrupt vector table, builds page tables, identity
   maps ROM, RAM and the I/O window, loads `PTBR`, and enables paging via
   `MCTL.PGE`.
7. The BIOS transfers control to the kernel entry point.

Because paging is off until step 6, all early accesses are physical. The
identity map means enabling paging does not move any address the BIOS already
uses. The guard page is never part of that map, so address zero stays invalid in
both modes.

### 7.2 Memory assumptions

- `0x00000000..0x0000FFFF` is the guard page and is never backed.
- `0x00000000..0xFFF0FFFF` is potential RAM; 128 MiB installed by default.
- `0xFFF10000..0xFFFEFFFF` is the memory-mapped I/O window.
- `0xFFFF0000..0xFFFFFFFF` is ROM: reset vector and BIOS.
- Nothing outside installed RAM and ROM is backed.

### 8.3 Object model

```text
struct Core {
    uint32_t regs[16];
    uint32_t pc, sp, flags;
    uint64_t cycles;
    uint32_t cr[12];              // CR0..CR11
    bool enabled, halted;
    uint32_t reservation;         // pending LL address
    bool reservation_valid;
};

class Memory {
    std::vector<uint8_t> rom;
    std::vector<uint8_t> ram;
    // read_physical / write_physical are internal to the MMU
};

class Mmu {
    TranslateResult translate(Core&, uint32_t va, Access, uint32_t size);
    void invalidate();
};

class Machine {
    Memory memory;
    Mmu mmu;
    std::array<Core, MAX_CORES> cores;
    std::vector<Device> devices;
    uint64_t ticks;               // global instruction clock, §13.5
    StepResult step(Core&);
    Core* next_core();            // deterministic round-robin, §12.3
};
```

The MMU is the single seam through which every guest access passes. Instruction
fetch, loads, stores, stack traffic, page-table walks, and vector-table reads all
use it. There is no TLB in v1, so `invalidate` has nothing to flush; the hook
exists so adding one does not change the call sites.

### 8.4 Error handling

Host-side problems are C++ exceptions caught at the CLI boundary: a source file
that does not assemble, a truncated image, a malformed `.kdbg`, an invalid
command line. Guest-visible faults are **not** exceptions; a fault is part of the
architecture and is delivered through the vector table.

```text
enum class Access { Fetch, Read, Write };
enum class FaultKind { InvalidOpcode, DivideByZero, Breakpoint, Page,
                       GeneralProtection, Alignment, DoubleFault };

struct Fault { FaultKind kind; uint32_t vector; uint32_t address; uint32_t code; };
struct StepResult { enum class Kind { Retired, Halted, Raised } kind; Fault fault; };
```

### 8.5 Command line

One executable with four subcommands:

```text
kr63 assemble    <source.asm> -o <image.rom> [--base <addr>] [--kdbg <image.kdbg>]
kr63 disassemble <image.rom> [--base <addr>] [--start <address>]
kr63 run         <source.asm|image.rom> [--bios] [--ram-size <bytes>] [--max-steps <n>]
kr63 dap
```

`--base` sets the address space the image is assembled for and defaults to the
ROM base, `0xFFFF0000`. Labels resolve to absolute addresses in that space, and
`.org` takes an absolute address.

### 8.6 Image format

A `.rom` file is a raw little-endian image loaded at the ROM base,
`0xFFFF0000`, with the entry pointer in its first word. Optional `.kdbg` sidecar
debug information is JSON and carries: format version, load base, source path,
entry address, symbol table, and the address-to-source-line map. The `.kdbg`
schema is pinned in M4; M0 only reserves format version 1 and the load-base
field. Keeping debug data out of the ROM means the boot image stays a plain
binary.

## 9. Assembler and Disassembler

### 9.1 Syntax

Case-insensitive mnemonics and register names, case-sensitive labels, `;`
comments, decimal and `0x` literals, `#` for immediate operands.

```asm
.word start
.text
start:
    MOV R1, #10
    MOV R2, #20
    ADD R3, R1, R2
    CMP R3, #30
    JZ success
    BRK
success:
    MOV R0, #0
    SYSCALL 32
```

Labels resolve to absolute addresses in the `--base` space, so the header word
above holds the ROM address of `start` rather than an offset from zero.

Supported memory forms: `[R5]`, `[R5 + 8]`, `[R5 - 4]`, `[SP + 8]`,
`[0x00100000]` and `[PC + label]` for PC-relative addressing.

### 9.2 Directives

`.word`, `.byte`, `.org`, `.text`, `.data`. `.text` and `.data` are section
markers, not linker sections. `.org` takes an absolute address in the space
established by `--base` and may only move forward within the image.

### 9.3 Scope

M0 implements the core subset directly from §4. M1 adds the remaining opcodes,
expressions and label arithmetic. Macros, relocations, separate RAM sections,
and a linker are out of scope for the first series of milestones.

The disassembler decodes a contiguous instruction range; it does not separate
code from data. Given a `.kdbg` sidecar it can annotate addresses with source
lines and symbols.

## 10. DAP and VS Code Debugging

### 10.1 Contract

The adapter speaks DAP over stdin/stdout using `Content-Length` framing; stdout
carries nothing but framed messages. Execution runs on a worker thread while the
main thread services requests. Transport, framing and message shapes follow the
DAP standard, so the VS Code extension only needs its executable path changed.

On Windows both streams must be switched to binary mode before the first frame
is written, or CRLF translation corrupts the headers; Linux needs nothing. That
switch is the only place the debug adapter is platform-aware.

### 10.2 Supported feature set

- `launch` (assembly source or raw ROM, with `.kdbg` when present) and
  `disconnect`; `attach` is out of scope until a transport exists
- `setBreakpoints`, `setInstructionBreakpoints`, `setDataBreakpoints`
- `continue`, `pause`, `next` (step over), `stepIn`, `stepOut`
- `stackTrace` with real frames, `scopes`, `variables` (registers, flags,
  control registers)
- `readMemory`, `writeMemory`, `setVariable`
- `evaluate` beyond register names: symbols from `.kdbg`, simple arithmetic, and
  `[address]` dereference
- `threads` reporting enabled cores

### 10.3 Debugger contract

- Programs load into ROM and, through the BIOS, into RAM.
- Source breakpoints resolve through the `.kdbg` line map; instruction
  breakpoints resolve to addresses; in-image `BRK` also stops execution.
- A stop returns the full core state, including `FAR`, `ESR`, and the flags.
- Memory reads and writes go through the MMU so the debugger sees the same
  addresses the guest does. Kernel-only pages are readable by the debugger even
  when the guest could not read them; this is a debugger privilege, not an
  architectural one, and is documented as such.
- Cores are debugged in all-stop mode: a breakpoint, step, pause, or fault on
  any core stops every core at an instruction boundary and reports which core
  stopped.

## 12. Multicore and Atomicity

v1 models 128 core slots but enables only core 0 at reset. This section defines
what happens once more than one is running.

### 12.1 Memory model

Guest memory is **sequentially consistent**. Naturally aligned 32-bit loads and
stores are indivisible, and every core observes a single total order of
accesses. `FENCE` is architecturally a full barrier but has no effect under this
model; it exists so a weaker model can be introduced later without changing
software.

Unaligned data accesses remain legal (§2.8) but are **not** atomic: a torn read
or write is possible, and software that races on them is relying on undefined
behaviour.

### 12.2 Atomic instructions

`LL` and `SC` are the only atomic read-modify-write pair:

| Instruction | Behaviour |
| --- | --- |
| `LL Rd, [addr]` | `Rd = memory[addr]`, then set this core's reservation to `addr` |
| `SC Rs, [addr]` | if the reservation covers `addr`, `memory[addr] = Rs` and `Z = 1`; otherwise no store and `Z = 0` |

Reservations are per-core and word-granular: a reservation covers the aligned
32-bit word containing the `LL` address. It is cleared by any store to that word
from any core, by `SC` itself whether it succeeds or fails, and by exception or
interrupt delivery. `SC` sets `Z` and leaves `N`, `C` and `V` unchanged; `LL`
preserves every flag.

Both instructions require a four-byte-aligned address inside RAM. An unaligned
address raises `#ALIGN`; a ROM, MMIO, or unbacked address raises `#GP`. Atomics
are deliberately not offered on device registers.

This pair is enough to build spinlocks, reference counts, and lock-free stacks
and queues, without the special-case decoding that a three-operand `CAS` would
need (§4.1).

### 12.3 Execution model

The reference execution model is a **deterministic cooperative scheduler**: one
host thread advances one enabled, non-halted core by one instruction per turn in
round-robin order, and delivers interrupts at instruction boundaries. Running
the same image from the same initial state therefore produces the same state
after any number of steps.

Devices advance at the start of each scheduler turn, before the interrupt check,
so asynchronous completions land at well-defined points (§13.5).

Host threads are an optional later backend behind the same interface. They are
not part of the reference model, because nondeterministic interleaving makes
regression tests flaky and makes a reproduced fault unreproducible.

### 12.4 Core lifecycle

A core is enabled by writing its slot in the inter-processor block at
`0xFFF10000`, the first MMIO page (§2.1). Core `n` occupies
`0xFFF10000 + 16 * n`, so all 128 slots fit inside that single page:

| Offset | Register | Meaning |
| --- | --- | --- |
| `+0x0` | `START_PC` | physical entry address; must be aligned and backed |
| `+0x4` | `START_SP` | initial stack pointer; zero means the top of installed RAM |
| `+0x8` | `CONTROL` | write bit 0 to enable; reads bit 0 = enabled, bit 1 = halted |
| `+0xC` | `IPI` | write an IRQ line 0..15 to raise it on this core |

A newly enabled core begins in kernel mode with interrupts disabled and paging
off, `PC = START_PC`, `SP = START_SP`, `FLAGS = K`, `COREID = n`, and every
other control register zero. Because paging is off, `START_PC` must be a
physical address in backed storage; the starter publishes a boot record in RAM
and points the new core at a trampoline that reads it and installs `PTBR` and
`MCTL` itself.

The block is mapped without the `U` bit (§2.7), so only the kernel can enable a
core. Enabling an out-of-range core, or supplying a misaligned or unbacked
`START_PC` or a misaligned `START_SP`, raises `#GP` on the writing core. There
is no instruction to stop a core; a core stops itself with `HALT`.

### 12.5 Inter-processor interrupts

Writing `IPI` for an enabled core sets that core's `IRQ` bit for the written
line, which is then delivered subject to that core's `IMR` and `IE` (§6.6).
Writes to a disabled core's `IPI` are ignored. This is the only way one core can
interrupt another; there is no broadcast.

### 12.6 What this model does not require

There are no per-core caches, so there is no coherence protocol, no invalidation
traffic, no store buffer, and no bus arbitration. Those concerns appear only if
caches are added later, and they are explicitly out of scope for v1.

### 12.7 Debugging

Cores are debugged in **all-stop** mode: a breakpoint, step, pause, or fault on
any core stops every core at an instruction boundary, and the adapter reports
which core stopped. `threads` lists the enabled cores. Single-stepping over an
`LL` loses the reservation, which is correct architectural behaviour and should
be documented for users.

## 13. Devices, DMA and Time

Devices are host-side models attached to the MMIO window. They never execute
guest code and never appear in the ISA; everything below describes how they fit
the memory, interrupt and time models already defined.

The window is allocated in the order given in §2.1: `0xFFF10000` is the
inter-processor block (§12.4), `0xFFF20000` is the IRQ route table (§13.6), and
device windows run from `0xFFF30000` to `0xFFFEFFFF`, twelve pages in all.

### 13.1 Trust and isolation

A device reaches memory through the same physical interface the MMU uses
(§2.7). It bypasses translation and permission checks entirely, so it can read
or write any backed RAM page, including kernel text and page tables. v1 has no
IOMMU and does not claim to isolate devices from the kernel. Devices are
trusted; the guard page is the only address they cannot touch, because it is not
backed.

### 13.2 DMA addressing

DMA addresses are **physical**, 32-bit, and restricted to installed RAM:

- a target outside backed RAM, including the guard page, ROM and the MMIO
  window, is a **device error** (§13.7), never a CPU fault;
- v1 supports a single `(physical address, length)` descriptor per transfer;
- scatter-gather, IOMMU translation and device-to-device transfers are out of
  scope.

Because the kernel is identity-mapped (§0, §2.7), a kernel buffer's virtual
address is already its physical address. A driver can hand that value to a
device with no translation step and no `virt→phys` helper.

### 13.3 Buffers

- **Kernel buffers** are used directly; identity mapping makes them valid DMA
  targets.
- **User buffers** are not. A user virtual address is unrelated to its physical
  address, so v1 drivers bounce transfers through a kernel buffer.
- A kernel page-table walker, possible because page tables live in RAM and the
  kernel may read them, is the later optimization that removes the copy.

### 13.4 Ordering

Under the sequentially-consistent model of §12.1, stores to a descriptor are
visible to the device before a later MMIO doorbell write. Drivers must still
issue `FENCE` between filling a descriptor and ringing the doorbell, so the code
stays correct if the memory model is ever weakened.

### 13.5 Time

The machine keeps `ticks`, a 64-bit count of retired instructions across all
cores. It is the only clock in the system; there is no wall-clock input.

- Devices advance at the start of each scheduler turn, before the interrupt
  check, so completions land at well-defined points.
- A device completes when `ready_at <= ticks`.
- A zero-latency device completes in the same turn in which it is started,
  which keeps simple tests synchronous.
- Because the scheduler is deterministic (§12.3), device timing is reproducible:
  the same image produces the same interrupt at the same tick.

### 13.6 Interrupt routing

The 16 hardware lines are steered by an IRQ route table at `0xFFF20000`, the
second MMIO page. Entry `n` names the target core for line `n`; the default is
core 0. Routing is applied when a device raises a line, and delivery is then
subject to that core's `IMR` and `IE` (§6.6). Cross-core interrupts written
through the IPP block (§12.5) bypass the table, because they already name their
target.

### 13.7 Device errors

A malformed transfer — an address outside backed RAM, a length that overruns it,
or a descriptor in ROM — is recorded in that device's status register and may
raise an interrupt. It is never reported as `#PF` or `#GP`, because those
describe CPU accesses, and it never writes outside the intended range.

### 13.8 Out of scope

No IOMMU, no scatter-gather, no cache maintenance (there are no caches), no
device hotplug, and no dependence on host wall-clock time.

## 14. Validation Checklist

The project is ready for OS work only when all of the following hold:

- **Arithmetic:** every arithmetic and logic opcode matches its flag table,
  including `MUL` overflow, `DIV`/`MOD`, and divide-by-zero.
- **Shifts:** counts 0..31 behave as specified, with correct carry-out.
- **Branches:** all conditional branches, `CALL`, and `RET` behave correctly.
- **Stack:** `PUSH`/`POP` and call frames restore `SP` exactly.
- **Memory widths:** 8-, 16-, and 32-bit loads and stores agree on endianness,
  zero-extension, and page-boundary crossing.
- **Exceptions:** `#UD`, `#DIV0`, `#BRK`, `#PF`, `#GP`, `#ALIGN`, and `#DF`
  deliver the documented frame, error code, and `FAR` value; `IRET` restores
  state, including mode and `SP`.
- **Privilege:** user mode cannot read or write control registers, `HALT`,
  `IRET`, or supervisor pages.
- **Paging:** identity mode and paged mode agree for the BIOS map; `U`/`W`/`X`
  are each enforced; `PTBR` misalignment faults; `PTBR` and `MCTL` writes
  invalidate translation state.
- **NULL safety:** the guard page faults on read, write, and fetch, both with
  paging off (`#GP`) and with paging on (`#PF`).
- **Atomicity:** `LL`/`SC` build a working spinlock; `SC` fails after another
  core writes the reserved word; unaligned and non-RAM atomics fault as
  specified.
- **Determinism:** two runs of the same multicore image end in identical state.
- **Core lifecycle:** a core enabled through the inter-processor block starts at
  `START_PC` in kernel mode with paging off and the documented register state,
  and invalid start addresses fault.
- **Inter-processor interrupts:** a cross-core `IPI` is delivered only when the
  target's `IMR` and `IE` allow it.
- **Devices:** a block-device DMA into a kernel buffer completes and raises the
  routed interrupt; a transfer outside RAM is a device error and corrupts
  nothing.
- **Time:** a timer interrupt arrives at the expected tick, and a second run
  reproduces the same tick.
- **Ordering:** a descriptor written before the doorbell is visible to the device
  under the sequential-consistency model.
- **Interrupts:** hardware lines obey `IMR`/`IE`, are delivered lowest-first,
  and never preempt while masked.
- **Debugger:** breakpoints, stepping, stack traces, memory reads and writes,
  and expression evaluation behave under the VS Code extension.
- **Portability:** the suite passes on MSVC, GCC and Clang, and a clean Linux
  clone configures and builds with no Windows-specific dependency.

  round-trip, and failure messages.
- Coverage measurement over `src/`, with tests added for uncovered branches.
- Confirm the GitHub Actions run is green on all three jobs and add a badge.

**Exit:** sanitizer-clean; property tests run at least 10^5 inputs each; CI
green on Linux (GCC, Clang) and Windows (MSVC).

### 16.2 M9 — Debugger completion

- Consume `.kdbg` when launching a raw `.rom`, supplying symbols and line
  mapping instead of instruction addresses only.
- Per-core shadow call stacks, so `stackTrace` is correct for any core.
- `setVariable` for registers and memory.
- Data breakpoints (watchpoints) triggered by guest stores.
- `evaluate`: symbols, arithmetic, `[addr]` dereference and register aliases.
- `restart` without relaunching.
- `attach` over TCP (`kr63 dap --listen <port>`), completing the DAP feature set.

**Exit:** protocol tests for every new request, and a documented attach session.

### 16.3 M10 — OS services and interrupt-driven I/O

- Syscall ABI: `open`, `read`, `write`, `close`, `brk`, `exit`.
- An interrupt-driven block driver: submit, sleep, wake on the completion IRQ,
  instead of polling the status register.
- A small user runtime in assembly providing `puts`, `read` and `exit`.
- A loader for more than one user program.
- User heap and a growable stack.

**Exit:** a demo reads blocks from the disk and prints them on interrupt, with no
polling loop anywhere.

### 16.4 M11 — Toolchain maturity

- `.equ`/`.set` constants and `.include`.
- Macros.
- `--listing` output: address, encoded bytes and source line.
- A multi-segment image container, so a RAM-resident program can be assembled
  directly instead of being copied and relocated by hand.
- Disassembly annotated with symbols and source lines from `.kdbg`.
- Diagnostics carrying line, column and a source excerpt.

**Exit:** assembler feature tests, and a multi-segment image that boots without
modification.

### 16.5 M12 — Parallel execution and concurrency

- An optional host-thread backend behind the same `Machine` interface, keeping
  the sequential-consistency contract and introducing no data races.
- Per-core debugger state and correct all-stop semantics under threads.
- A scheduling quantum knob.

**Exit:** the whole suite passes in both serial and parallel modes, plus a stress
test of the `LL`/`SC` spinlock across real threads.

### 16.6 M13 — Device platform

- Device discovery: a device table or tree the kernel reads, replacing hard-coded
  base addresses.
- A console input device.
- `--disk <file>` to back the block device with a host file, persisted on write.
- Scatter-gather DMA descriptors.

**Exit:** the BIOS discovers devices, and a demo reads console input and writes
it to disk.

### 16.7 M14 — Performance (optional)

Only if a workload justifies it: a TLB, a decoded-instruction cache, bulk memory
operations. No target numbers are set, because nothing currently needs them.

### 16.8 Deliberately out of scope

- Networking, graphics and USB.
- Symmetric-multiprocessing scheduling beyond the cooperative model.
- Device hotplug and an IOMMU.

The C and C++ toolchains were out of scope here; they are now planned in §17.

## 17. C++ Toolchain (proposed)

> **Status: proposal, no code written.** This section summarises
> `docs/cpp-plan.md`, which in turn rests on
> `docs/cpp-compiler-research.md` (front-end choice) and
> `docs/c-compiler-research.md` (the C compiler and shared back end). Neither
> the C compiler nor any C++ work exists in this tree today: everything below is
> future work. Where the imported plan and this document disagree on numbering,
> this document wins — see §17.2.

### 17.1 Decision: one repository, a `cxx/` subtree, EDG kept external

The C++ toolchain lives in this repository under a new top-level `cxx/`
directory, sharing a `backend/` library with the C compiler. EDG is **not
vendored**: `tools/edg/` holds a pinned commit and scripts that fetch and build
it into an external cache.

The argument is coupling: the back end must emit exactly the encodings in
`src/isa.cpp`, both compilers must agree with one `docs/abi.md`, images must
load through the existing boot path, and `.kdbg`/DAP must understand C++ lines
and names. An ABI change is one atomic change in a monorepo and four coordinated
cross-repository changes otherwise. EDG is ~1.3 M lines and minutes to build, so
vendoring would grow the repository permanently and make every CI run pay for it.

New layout:

```text
backend/        shared KIR, codegen, frames, ABI, emit, image/weak merge
cxx/            driver, EDG glue, lowering, C++ data, runtime, headers, tests
tools/edg/      PINNED, fetch/build/verify scripts, optional patches
docs/abi.md     the single C/C++ ABI contract (to be written)
docs/isa-v1.1.md, docs/cxx.md, docs/edg-notes.md
tests/abi/      shared ABI conformance tests
examples/cxx/   C++ smoke tests
```

Ownership boundaries: `backend/` contains no front-end-specific code; `cxx/`
may depend on `backend/` and `kr63_core`, never on `cc/` internals; `tools/edg/`
never contains EDG source.

### 17.2 Milestone numbering: P-workstream, then M15–M19

`docs/cpp-plan.md` assigns its prerequisites to "M8", "M9" and "M10–M14". Those
are milestones of the **C-compiler plan**. In this document M8–M14 are already
complete and mean verification, debugger, OS services, toolchain, parallelism,
devices and performance — none of which is a C compiler.

To keep the two readable, this document renames the prerequisites to a **P
series** and reserves **M15–M19** for the C++ work. Nothing about the C++
content changes; only the labels.

| ID | Prerequisite | Why C++ needs it |
| --- | --- | --- |
| P1 | ISA v1.1: `ADJSP`, `JLT`/`JGE`/`JLE`/`JGT`, `LOAD8S`/`LOAD16S`, `SAR`, `DIVS`/`MODS` — **done**, docs/isa-v1.1.md | frames, `setjmp`/`longjmp`, signed comparisons and arithmetic |
| P2 | Assembler: `.space`, `.align`, `.asciz`, local labels, region-aware image cap — **done** | C++ data, BSS, string literals, images over 64 KiB |
| P3 | C compiler plus the shared KIR back end, with `docs/abi.md` frozen | bootstrap mode; one ABI for both languages |
| P4 | Image builder with weak/COMDAT merging | vtables, inline functions, template instantiations |
| P5 | `.kdbg` v2 (files, lines, functions, variables) | C++ source debugging |
| P6 | Loader for RAM images larger than the 64 KiB ROM page | C++ images exceed both the ROM and the BIOS blob |
| P7 | A `LICENSE` in the repository | required before distributing anything built with EDG |

**P1 changed a frozen document.** §3 and `docs/isa-v1.md` freeze ISA v1;
v1.1 is a separate revision, now written up in docs/isa-v1.1.md with ten new
opcodes in the previously reserved  x2F– x38 range. It is backward
compatible: every v1 image runs unchanged.

P1 and P2 are complete. P3–P7 are not. **M15 can start immediately** (it needs
only the EDG checkout and a host compiler); **M16 cannot** — it needs P3.

### 17.3 Milestones

Estimates are person-weeks for one experienced developer, matching
`docs/cpp-compiler-research.md` §12.

**M15 — EDG spike and pin (1–2 weeks).** `tools/edg/PINNED`; fetch/verify
scripts; staged build copy with our `defines.kr63.h`; `target.kr63.h` asserting
ILP32, little-endian, 64-bit `long long`, lowered exceptions. Compile a sample
with classes, virtual functions, templates, RAII, `new`/`delete` and exceptions,
and compile its generated C with host GCC. Exit: one command builds EDG on both
hosts, and the IL layout assertions match the expected model.

**M16 — C++ via the C back end (3–5 weeks).** `kr63-cxx` bootstrap driver:
`edgcpfe` → `foo.int.c` → the C compiler → image. Runtime built from EDG's C++
sources translated to C; `crt0` runs `__sti__`; `operator new`/`delete` over the
kernel allocator. `#line` recorded so `.kdbg` points at the `.cpp`. Exit: a C++
program with classes, templates, virtual dispatch, `new`/`delete` and
exceptions runs on the emulator with correct output.

**M17 — Native backend core (6–9 weeks).** EDG IL reader, `cxx/lower/` to KIR,
codegen and weak/COMDAT merge; `kr63_be` built against the staged EDG source
(file-based IL first, in-process later only if profiling justifies it). Exit:
the C++ integer/pointer corpus produces identical output in both modes, and a
10 k-line program links.

**M18 — C++ runtime and ABI (4–6 weeks).** vtables and dispatch, ctor/dtor
wrappers, RTTI (`typeid`, `dynamic_cast`), exceptions over `setjmp`/`longjmp`
with cleanup regions, guard variables and static-init ordering. Exit: the
exception/RTTI suite passes, EDG's `lib_src` compiles, and a C++ kernel demo
runs.

**M19 — Debug, tooling, validation (3–4 weeks).** `.kdbg` v2 from IL source
positions, demangled names, DAP support for `.cpp`, `kr63 c++` folded into the
CLI last, differential testing against host `g++ -m32`. Exit: VS Code
breakpoints and stepping work on a `.cpp` file.

Total 4–6 months, with a bootstrap compiler working after roughly two.

### 17.4 Build integration

Root `CMakeLists.txt` gains options only — `KR63_ENABLE_C`,
`KR63_ENABLE_CXX`, `KR63_EDG_ROOT`, `KR63_EDG_BUILD`, `KR63_EDG_MODE`
(`bootstrap` | `native` | `both`), `KR63_CC_EXECUTABLE` — plus
`add_subdirectory(backend)` and `add_subdirectory(cxx)` behind them. Existing
targets are unaffected.

Configure never touches the network. Fetching and building EDG are explicit
steps (`tools/edg/fetch`, `tools/edg/build`) verified against `PINNED`, and CI
caches the EDG build keyed on that pin. With `KR63_ENABLE_CXX=ON` and no EDG,
bootstrap mode still configures and reports a useful error at run time; native
mode fails configure with an actionable message.

Two modes: **bootstrap** runs EDG's C-generating back end and our C compiler;
**native** reads EDG's IL and emits KR63 assembly. The plan is bootstrap first,
file-based IL second, in-process backend last.

The driver is `kr63-cxx <files> -o <image> [--base] [--kdbg] [-I] [-D] [--std]
[--mode] [--dump-il] [--il-file] [-S] [-g] [--no-exceptions] [--no-rtti]
[--keep-temps]`. It ships as a standalone executable; folding it into the CLI as
`kr63 c++` is deliberately the last change, so early milestones do not collide
with CLI work.

### 17.5 ABI and runtime

One ABI document, owned jointly with the C compiler: ILP32, register roles,
aggregate passing, hidden returns, varargs, frames and callee-saves, atomics and
`volatile`, plus C++ specifics (`this` first, Itanium vtable layout, exception
runtime calls, static-init ordering). Conformance tests live in `tests/abi/` and
are shared by both compilers.

Runs on KR63 and is compiled by our own toolchain: the C/C++ runtime, EDG's
`lib_src` runtime (EH, RTTI, `new`), and a freestanding header set —
`<cstddef>`, `<cstdint>`, `<limits>`, `<new>`, `<typeinfo>`, then
`<type_traits>`, `<utility>`, `<initializer_list>`, `<array>`, `<bit>`,
`<optional>`, `<atomic>`, and optionally a small `std::string`/`std::vector`/
`std::unique_ptr` subset.

Does not run on KR63: `edgcpfe`, the drivers, the header trees.

Out of scope for v1: `float`, threads, `<filesystem>`, `<iostream>`, TLS,
coroutines, modules, and `libc++`.

### 17.6 Risks and open questions

The sharp ones: EDG's build against VS2026 may differ from its documented
baseline; a missing weak/COMDAT merge breaks template-heavy code; EDG's
exception runtime is `setjmp`-based and not the Itanium ABI, so `libc++`
interop would need an adapter later; no standard library exists; and every
prerequisite above is unbuilt work.

Open questions for before M17: file-based IL reader first or in-process first;
Itanium EH eventually or `setjmp` permanently; one EDG front end for both C and
C++, or chibicc stays for C; how much of a standard library to write; and where
a toolchain install lives so `kr63 c++` can find headers and runtime.

### 17.7 Licensing

EDG is Apache-2.0 with LLVM exceptions. EDG source is not redistributed here by
default — the scripts point at upstream plus a commit. Guest images do contain
EDG's runtime compiled from `lib_src`, so a notice belongs in the image
documentation. The repository still has no `LICENSE`; P7 covers that.
